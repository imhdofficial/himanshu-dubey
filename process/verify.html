PROCESS / 04 / VERIFY

edges.

Quality is usually lost at the edges: a small viewport, long title, slow request, keyboard user, unexpected CMS entry or browser difference. Verification deliberately visits those edges before users do.

THE STANDARD

Do not test the screenshot. Test the product.

A confident release comes from checking behavior, content extremes, devices, browsers and accessibility states—not from one final visual review on the machine that built it.

VIEWPORTSmall → large
INPUTMouse + keyboard + touch
NETWORKFast + slow + failure
REGRESSIONShared components
WHAT GREAT LOOKS LIKE
01

Test with content stress

Long labels, empty lists, missing images and large values reveal layout weakness.

02

Use multiple input methods

Keyboard and touch expose interaction assumptions mouse testing hides.

03

Check the failure path

Timeout, validation and API errors should give the user a clear recovery action.

04

Regression-test shared changes

One CSS or component change can affect many pages; verify the system, not only the edited screen.

PRACTICAL METHOD
01

Run viewport matrix

Check key breakpoints and the widths between them.

02

Run state matrix

Visit ready, loading, empty, error, success and disabled states.

03

Check accessibility

Verify focus order, contrast, labels and keyboard interaction.

04

Inspect performance

Look for layout shift, heavy media, blocking scripts and unnecessary motion.

05

Regression pass

Revisit connected pages and components before release.
